# Codebase audit — July 2026

Every item below was verified against the source, not inferred from naming. Where
severity depends on something I checked (a route guard, a `disabled` attribute),
that check is stated.

Two things worth reading first:

- **The single reason checkout "doesn't really work" is item O-1.** There is no
  customer-facing order endpoint. No amount of frontend wiring fixes that.
- **The most dangerous defect was F-1**, because it failed silently and in the
  direction of dispensing prescription-only medicine without a prescription.

---

## Fixed in this branch

### F-1 — The prescription gate could never fire *(pharmacy safety)*

`app/checkout/page.tsx` gated Rx-only items on:

```ts
cart.some(item => item.requiresPrescription === true)
```

`CartItem` declared `requiresPrescription?: boolean`, but `CartContext.addToCart`
built its cart objects from `id, name, price, image, qty, category, mrp` — the
field **was never assigned, anywhere in the codebase**. The expression was
therefore unconditionally `false`, so the prescription modal never appeared and
prescription-only products checked out freely.

The data existed the whole way down: `backend/src/products/entities/product.entity.ts`
has `prescription_required: boolean`. Only the wiring was missing.

Fixed by threading the flag from all three `addToCart` call sites through
`ProductInput` into `CartItem`, via a shared `isPrescriptionProduct()` helper that
accepts both the API's `prescription_required` and the frontend's
`requiresPrescription` spelling.

> Still required: this is a **client-side** gate. It must also be enforced when
> the order endpoint in O-1 is built. A cart in `localStorage` is user-editable.

### F-2 — Rx check trusted a caller-supplied bypass flag

`handlePayment(bypassRx = false)` skipped the prescription check whenever the
caller passed `true`, which the Rx modal's confirm button did. The button carries
`disabled={!isRxUploaded}`, so this was **not** directly exploitable — a correction
to my first reading of it. But `disabled` is a UI hint, not an enforcement point,
and the gate's correctness depended on every call site being trustworthy. The
parameter is gone; the check re-derives from state.

### F-3 — `"toString"` was a valid coupon code

```ts
setIsOfferApplied(offerCode in VALID_COUPONS);
```

`in` walks the prototype chain. Verified in node: both `'toString' in VALID_COUPONS`
and `'constructor' in VALID_COUPONS` evaluate to `true`. Either string applied a
real discount. Now uses `Object.hasOwn`.

### F-4 — Every coupon gave 10%, whatever it was worth

The discount used a flat `SHIPPING_CONFIG.COUPON_DISCOUNT_PERCENT` (10) for all
codes, so `NEW15` — defined as 15% in `VALID_COUPONS` — quietly paid out 10%. The
per-coupon `discount` and `type: 'percentage' | 'fixed'` fields were dead. Now
honoured, with the discount clamped to the cart total.

### F-5 — Discount survived editing the coupon field

Applied state was a boolean, so entering `NEW10`, pressing Apply, then editing the
input to anything at all kept the discount while displaying "Invalid or expired
code". Now stores the code that was actually applied, and editing retracts it.

### F-6 — Social login fabricated sessions client-side

`AuthContext.login()` with a `socialToken` never contacted the server. It built a
`User` from the submitted email, wrote it plus the token to `localStorage`, and
redirected to `/dashboard`. Any caller could mint a session for any address. No
social endpoint exists on the API, so this now fails with a clear message instead
of pretending to succeed.

### F-7 — `localStorage` role granted the admin dashboard

`initializeAuth` short-circuited server validation for 10 minutes and restored the
user — including `role` — straight from `localStorage`. `AdminRoute` gates on
nothing but `isAdmin`. Editing one devtools value rendered the entire back-office.

The API's own endpoints are separately JWT-guarded, so this exposed the admin
**UI** and whatever it renders client-side, not admin data from the server. Still
a privilege-escalation surface. Identity now always comes from `auth/me`.

### F-8 — SQL injection vector in order sorting

```ts
queryBuilder.orderBy(`order.${sortBy}`, sortOrder);
```

`sortBy` was `@IsOptional() @IsString()` with no allowlist, and TypeORM does not
parameterise identifiers — it interpolates them. Reachable only with a valid admin
JWT (every route in `orders.controller.ts` carries `JwtAuthGuard, AdminGuard`), so
this is authenticated rather than anonymous. Now allowlisted, with `sortOrder`
constrained to `ASC`/`DESC`. Covered by a test that feeds it
`id; DROP TABLE orders; --`.

### F-9 — Pagination accepted NaN and unbounded page sizes

`parseInt('abc')` is `NaN`, and `.skip(NaN)` throws at the driver; `limit=100000`
was honoured. Now clamped to 1..100 with sane fallbacks.

### F-10 — Order totals were whatever the client said

`create()` spread the request straight onto the entity, so `totalAmount` was
caller-supplied and never checked against the line items. Currently admin-only
(see F-8 on guards), so this is a data-integrity bug today rather than a payment
exploit — **but it becomes price tampering the moment O-1 is built.** Totals,
subtotal and item count are now derived server-side, with discounts rejected when
they exceed order value.

Item unit prices are still taken from the request, which is defensible only while
this endpoint is admin-only. A code comment marks this as blocking for O-1.

### F-11 — Money arithmetic drifted, and would have produced NaN

`19.99 * 3` is `59.970000000000006`; Postgres rounds on write, so stored totals
stopped matching the sum of stored line items. Now rounded to 2dp.

While writing that helper I hit a second problem: `taxAmount` and friends are
`decimal` columns, which node-postgres returns as **strings** to preserve
precision, even though the entities type them as `number`. `"5.00" + Number.EPSILON`
string-concatenates and then coerces to `NaN`. The helper coerces explicitly. See
O-9 — the underlying type mismatch is repo-wide and unfixed.

### F-12 — `sanitizeUrl` broke every absolute URL during SSR

It referenced `window.location.origin` unconditionally. On the server that throws
`ReferenceError`, which its own `catch` swallowed, returning `'#'` — so
server-rendered links pointed at `#` and then changed after hydration. Relative
URLs are now short-circuited before parsing and a fallback base is used on the
server.

### F-13 — The AI endpoint was unauthenticated

`POST /api/ai/chat` had no auth check. Any anonymous request drove an OpenAI
completion on the deployment's key. Now requires a valid admin bearer token.

### F-14 — The AI assistant invented operational data

On any failure — missing key, bad key, quota, network — the route fell through to
canned replies: `"Inventory status: 98% healthy"`, `"I found 5 pending orders"`.
These rendered in the admin console indistinguishably from real figures. Fabricated
inventory numbers in a pharmacy back-office are worse than an error message. The
route now returns 503/502, the system prompt forbids inventing figures, and the
client surfaces the failure instead of replacing it with "I'm currently in demo
mode".

### F-15 — Five backend tests were already failing on `main`

`products.service.spec.ts` hand-rolled a query-builder stub per test, listing only
the chain methods the service called at the time. The service later added
`.leftJoin()`, `.select()` and `.groupBy()`, so the stubs threw "is not a function".
The assertions also targeted a removed `getRawAndEntities` contract. Verified as
pre-existing by running the suite on a clean checkout. Replaced with a single
chainable factory and assertions against current behaviour.

Suite went from 11 passed / 5 failed to **27 passed**, including 11 new tests
covering F-8 through F-11.

### F-16 — Repository hygiene

- `lib/icons.tsx`: a 258-line near-duplicate of `lib/icons.ts`. Both resolved to
  the `@/lib/icons` specifier used by 70 importers; TypeScript picked the `.ts`,
  making the `.tsx` dead. Its one unique export had no importers.
- `register_payload.json`: contained a plaintext password. **See O-10.**
- `services.json`, `service_id.txt`, `deploy_trigger.txt`: deploy-provider
  internals.
- `backend/backend_log_final.txt`: a 768 KB UTF-16 terminal capture with ANSI
  escapes.
- `public/data/products.json`: **not** dead — it feeds `scripts/seed_db.js` — but
  under `public/` Next served 283 KB of generated fixtures to every visitor. Moved
  to `scripts/data/` and gitignored.
- `docker-compose.yml` declared Redis, Weaviate and MinIO. Nothing in the repo
  opens a connection to any of them; ~2 GB of RAM per `docker compose up`.
- A third copy of `safeNumber` lived in `ProductCard.tsx` (alongside `lib/utils.ts`
  and `CartContext.tsx`). Now imported.
- Five deployment guides contradicted each other on Vercel-vs-Render and all told
  the reader to set `CORS_ORIGINS`, which the app never reads — `main.ts` reads
  `ALLOWED_ORIGINS`. Following the docs left the frontend failing CORS against its
  own API. Consolidated into `docs/deployment.md`.
- `docs/openapi.yaml` documented port 8000; the API listens on 4000.

## Resolved in the second pass

### O-1 — Customer order endpoint *(fixed)*

`POST /v1/orders/quote` and `POST /v1/orders/checkout`, authenticated as the
customer. The browser sends product ids and quantities only. The server resolves
prices from the catalogue, validates the coupon through `CouponsService`, enforces
the prescription rule, allocates stock FEFO under a row lock, and creates the order
— all in one transaction. `handlePayment` now awaits a real order and redirects
with its id.

### O-1b — Migration 001 could never run *(fixed, found while building O-1)*

`orders.user_id` and `order_items.product_id` were declared `UUID REFERENCES
users(id)` / `products(id)`, but both targets are `SERIAL` integers. Postgres
rejects a UUID→integer foreign key, so the script aborted and **the orders tables
were never created in any database.** Corrected to `INTEGER`, with entities and
DTOs aligned. This was the deepest reason nothing could be anything but a mock.

### O-2 — Prescription upload *(fixed)*

Real `prescriptions` table and module: multipart upload with the size cap enforced
by multer before buffering, MIME type cross-checked against the file's magic
number, path separators stripped from the filename, bytes stored as `bytea`
(container disk is ephemeral), `select: false` so listings don't stream scans, and
ownership folded into the lookup so another account's id can't be attached to an
order. Orders link to the prescription they were dispensed against.

### O-4 — Duplicated coupon and pricing rules *(fixed)*

Rules now exist only in `backend/src/orders/order-pricing.ts`. Checkout renders
`/quote`; the cart is explicitly a preview. What survives in `lib/constants.ts` is
marketing copy, renamed `PRICING_COPY`. A coupon and the UPI discount no longer
stack — the customer gets whichever is larger, where previously any coupon
silently discarded a bigger UPI discount.

### O-5 — Password reset tokens *(fixed)*

Moved to a `password_reset_tokens` table storing only the SHA-256 hash, with
`used_at` so a token cannot be replayed and opportunistic eviction of expired rows.

### O-6 — Empty admin shells *(deleted)*

Removed Attendance, Rules Engine, Pharmacist, Warehouse (+init), CMS (+builder),
Exports, Delivery, Returns, Finance (+payroll) and Support — roughly 2,000 lines.
Verified first that `/api/v1/cms/pages`, `/api/v1/delivery/zones`,
`/api/v1/exports`, `/api/v1/finance/dashboard`, `/api/v1/returns/*` and `tickets`
have no implementation anywhere in the backend: every one of those pages called a
404. Navigation trimmed to the pages backed by a real module. These are back-office
concerns and belong to the POS product.

### O-7 — Stock decrement *(fixed)*

`CheckoutService.allocateStock` reserves FEFO (first-expired-first-out, so
near-dated stock ships before it has to be written off), skipping expired batches,
under `pessimistic_write` so concurrent checkouts cannot both claim the same units.

### O-8 — Password policy *(fixed)*

Client minimum raised from 6 to 8 via an exported `MIN_PASSWORD_LENGTH`, matching
`registerSchema` and `resetPassword`.

### O-9 — `decimal` columns *(fixed)*

`moneyTransformer` applied to every money column, coercing on read and rounding to
2dp on write.

### Customer order history *(fixed)*

`GET /v1/orders/mine`, and the dashboard now fetches it. That page was a
module-level `const ORDERS: any[] = []` beneath a comment claiming orders were
"loaded from the backend".

## Resolved in the third pass

### O-3 — Saved address book *(fixed)*

`addresses` table, module and API. One default per customer enforced by a partial
unique index rather than by application code remembering to clear the old one;
deleting the default promotes another so checkout always has something
preselected. Checkout loads the book and preselects the default instead of holding
addresses in React state keyed by `savedAddresses.length + 1`.

### Remaining stub pages *(fixed or deleted)*

- **Homepage** rendered nothing to buy: featured products, health goals and the
  "why us" panel were all `any[] = []`, so three sections showed placeholder text
  to every visitor. Products now come from the catalogue; the other two were
  marketing copy and are now real static content.
- **Saved items** was linked from three places and backed by nothing. Now a
  `saved_items` table with an idempotent add. Its "Smart Suggestions" panel,
  captioned *"Based on your preferences"*, was removed — there is no
  recommendation engine and it was a promise the product could not keep.
- **Prescriptions** page: its upload card was a styled `div` with no file input
  behind it. Now wired to the real upload. Its detail modal displayed a doctor's
  name, an expiry date, "Extracted Medicines" and pharmacist notes — none of which
  exist anywhere in the system. Replaced with what is actually stored.
- **Admin staff** requested `apiUrl('employees')`, an endpoint no controller
  serves, with no `Authorization` header (so the route's `AdminGuard` would have
  rejected it anyway), then cached the result in `localStorage` and preferred that
  cache forever after — making a failure indistinguishable from an empty team.
- **`/doctors`** deleted: an orphan page, no backend, no inbound links.

## Still outstanding

### O-10 — The committed password is still in git history

Deleting `register_payload.json` removes it from `HEAD`, not from history. The
credential (`verify_live_user@pulsekart.in`) must be rotated, and the history
rewritten or that account treated as compromised. **This is the one item here that
needs action outside the codebase.**

### O-12 — No payment gateway

Orders are created `PENDING`. Nothing charges the customer; marking an order
`PAID` belongs to a gateway webhook (Razorpay/Stripe), which is not wired up. The
checkout flow is complete and correct up to the point of taking money.

### O-11 — Rate limiting is per-instance and in-memory

`ThrottlerModule` uses the default in-memory store, so limits are per process and
reset on restart. Fine for one instance; misleading as a security control beyond
that.
