# Deploying PulseKart

This replaces the previous `QUICK_DEPLOY.md`, `DEPLOYMENT.md`, `CUSTOM_DOMAIN.md`,
`DOMAIN_SETUP_VISUAL.md` and `MAINTENANCE.md`, which contradicted each other on
the two points that actually matter: where the frontend runs, and what the CORS
environment variable is called.

## The one thing the old docs got wrong

The backend reads **`ALLOWED_ORIGINS`** (see `backend/src/main.ts`). The old
guides told you to set `CORS_ORIGINS`, which the application never reads. If you
followed them, the backend silently fell back to `http://localhost:3000` and every
browser request from your deployed frontend failed CORS.

Use `ALLOWED_ORIGINS`. It is a comma-separated list of exact origins:

```
ALLOWED_ORIGINS=https://www.yourdomain.com,https://yourdomain.com
```

Do not set it to `*` in production. `main.ts` logs a warning if you do, and with
`credentials: true` a wildcard origin is rejected by browsers anyway.

## Deployment target

Everything runs on Render, driven by `render.yaml` at the repo root: a Postgres
database, the NestJS API, and the Next.js frontend. Do not also deploy the
frontend to Vercel — running two frontends against one API is what produced the
conflicting CORS advice in the first place.

## First deploy

1. Push your branch to GitHub.
2. Go to <https://dashboard.render.com/blueprint/new> and connect this repo.
3. Render reads `render.yaml` and creates `pulsekart-db`, `pulsekart-api` and
   `pulsekart-web`. Click **Apply** and wait 5-10 minutes.
4. On the `pulsekart-api` service, set `ALLOWED_ORIGINS` to the frontend URL
   Render assigned (or your custom domain, once configured below).

`JWT_SECRET` is generated by Render. `DATABASE_URL` is wired to the database
automatically — you do not need to set either by hand.

### Database schema

`DB_SYNC` controls TypeORM `synchronize`. Leave it **unset** in production;
TypeORM's auto-sync will happily drop columns it thinks are unused. Apply the SQL
in `backend/src/database/migrations/` instead.

### Verify

```bash
curl https://pulsekart-api.onrender.com/v1/health
```

## Custom domain

Add the domain on the `pulsekart-web` service (Settings → Custom Domains), then
create these records at your DNS provider:

| Type            | Name  | Value                        |
| --------------- | ----- | ---------------------------- |
| CNAME           | `www` | `pulsekart-web.onrender.com` |
| ALIAS / ANAME   | `@`   | `pulsekart-web.onrender.com` |

If your provider does not support ALIAS/ANAME at the apex, use an `A` record
pointing at Render's documented apex IP — check
<https://render.com/docs/custom-domains> for the current value rather than
copying an IP out of a guide, as it has changed before.

DNS takes 5-30 minutes; SSL is issued automatically once Render verifies the
records. **After the domain resolves, update `ALLOWED_ORIGINS` on the API to the
new origin** or the frontend will fail CORS against its own backend.

## Shipping updates

Render auto-deploys on push to the tracked branch:

```bash
git add .
git commit -m "Describe your change"
git push origin <your-branch>
```

Confirm which branch each service tracks in the Render dashboard — it is per
service, and the old docs referenced a branch that no longer exists.

To change secrets, edit them under Environment on the service; saving triggers a
redeploy. To undo a bad deploy, use Deploys → the last green entry → Rollback.

## Free-tier behaviour

The API sleeps after 15 minutes of inactivity, so the first request after idle
takes 30-60 seconds. This is the free plan working as designed, not a bug.
